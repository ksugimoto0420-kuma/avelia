# サイン入りデジタル写真集 技術調査レポート

出版社と協業してデジタル写真集にサインを付与し、ユーザーが手軽に閲覧できる
仕組みを実現するための事前調査。bookend（KEYRING.NET）が業界標準だが、
コスト面・運用面で課題があるため、代替案を比較する。

## 1. 出版業界における「保護された電子書籍配信」の標準構造

電子書籍配信は概ね3層構造：

### Layer 1: コンテンツのコンテナ形式
- **PDF**：レイアウト固定、写真集と相性◯
- **EPUB**：リフロー型 / レイアウト固定型（fixed-layout）
- 写真集はレイアウト保持が重要なので **PDF or EPUB fixed-layout** が主流

### Layer 2: DRM（不正コピー防止）
- **強DRM**：暗号化 + 認証サーバで都度復号鍵を発行、専用ビューワで閲覧
- **ソーシャルDRM**：暗号化なし、購入者情報を**透かし**として埋込、流出時に追跡

### Layer 3: ビューワ
- **Webブラウザ閲覧**（PDF.js / Readium Web Player など）
- **専用アプリ閲覧**（iOS/Android、bookend など）

## 2. 主要選択肢の比較

### 選択肢A：bookend（KEYRING.NET）

業界実績：sukisuki も採用、ダブルの「PLANETS」も採用。

| 項目 | 内容 |
|---|---|
| 仕組み | DRM対応PDF/EPUBをクラウド配信、専用ビューワで閲覧 |
| コスト | **初期240万円 + 年間ランニング160万円** + ユーザー単価 |
| 保護機能 | 暗号化・印刷制御・画面キャプチャ防止・閲覧期間制限・端末台数制限 |
| 個別情報埋込 | ソーシャルDRMで透かし可（メアド等を動的埋込） |
| 対応 | iOS, Android, Webブラウザ |
| 出版社連携 | Shopify連携など出版社向け運用ノウハウあり |

**サイン入り写真集の運用想定**：
1. 出版社からベース写真集（PDF）を受領
2. Avelia 側でアーティストがサインを描く → ベース + サイン を結合した個別 PDF を生成
3. bookend にユーザー単位でアップロード
4. ユーザーは bookend ビューワで閲覧

### 選択肢B：Readium LCP（オープンソース）

| 項目 | 内容 |
|---|---|
| 仕組み | EPUBに暗号化、LCP License Server がライセンス発行 |
| コスト | **EDRLab認証 年間費用のみ、取引手数料ゼロ** |
| 保護機能 | 暗号化・閲覧期限・端末台数制限・コピー保護 |
| 個別情報埋込 | ライセンスにユーザー情報を埋め込み可 |
| 対応 | Readium ベースのアプリで閲覧（自社アプリ実装可能） |
| 開発コスト | License Server（Go）+ 閲覧アプリ開発が必要 |

非営利の EDRLab が提供するオープン標準。**自社開発寄りの選択肢**。
コストは抑えられるが閲覧アプリと連携サーバを自前で組む必要あり。

### 選択肢C：自社開発（Webブラウザ閲覧）

| 項目 | 内容 |
|---|---|
| 仕組み | PDF.js / カスタムビューワでブラウザ閲覧、自社サーバから署名付き URL で配信 |
| コスト | **開発コストのみ**、ランニングは S3 等のストレージ + CDN |
| 保護機能 | 限定的：右クリック・DL禁止・透かし埋込・スクショは防げない |
| 個別情報埋込 | 自由に実装可能（サイン・宛名・購入者名のオーバーレイ） |
| 対応 | Webブラウザのみ（オフライン不可） |
| 開発コスト | 中：PDF.js拡張 + 個別PDF生成 + 配信API |

**最も実装の自由度が高い**が、強いDRM保護はできない。
スクショ・写真撮影で漏洩リスクあり。

## 3. 「サイン入り」を実現する3つの実装パターン

サイン入り写真集の本質は **「ベース写真集 + 個別サイン画像 = 個別納品物」**。

### パターンX：ファイル合成型（一般的）
1. アーティストが Avelia 管理画面でユーザーごとに「サイン+宛名」を描く
2. サーバー側で **ベース写真集PDFの最終ページにサインPDFを結合**して個別PDFを生成
3. 生成された個別PDFを保護配信（bookend、LCP、自社）

- メリット：シンプル、出版社のコンテンツに手を加えない
- デメリット：1ユーザーごとにファイル生成・保存が必要（容量増、バックエンドジョブ要）

### パターンY：オーバーレイ型（閲覧時合成）
1. ベース写真集（共通）と、サイン画像（個別）を別管理
2. 閲覧アプリ・閲覧ページが2つを **その場で重ねて表示**
3. ダウンロード不可、Webアプリのみで成立

- メリット：ファイル肥大化なし、サインの修正・差し替えが容易
- デメリット：ダウンロード提供不可、専用閲覧UIが必須

### パターンZ：ソーシャルDRM型
1. ベース写真集の各ページに、購入者名/メール/購入IDを **透かし**として埋込
2. DRMは付けず、ダウンロード可
3. 流出時に出所が追跡できる

- メリット：自由度が高い、配布が楽
- デメリット：暗号化なし、コピーは技術的には可能、「サイン」体験ではなく「透かし」

## 4. 自社開発で「全て賄える」か？

**結論：技術的には可能だが、保護レベルとコストで割り切りが必要**。

| 要件 | 自社開発で対応可？ |
|---|---|
| 個別サイン入りPDFの生成 | ◯ サーバーサイドで pdf-lib などで合成可能 |
| ベース写真集の保存 | ◯ S3 / Cloudflare R2 |
| 配信（署名付きURL） | ◯ 期限付きトークンで配信 |
| Webブラウザ閲覧 | ◯ PDF.js / 自前ビューワ |
| 印刷防止・コピー防止 | △ 簡易対策のみ、本気の不正は防げない |
| **スクショ防止** | ✕ どの仕組みでも完全防止は不可能 |
| 端末台数制限 | △ ログインセッションで簡易制限可、専用アプリより弱い |
| 暗号化＋復号制御 | △ 自社実装可だが安全な鍵管理が必要 |
| オフライン閲覧 | ✕ 専用アプリ必須 |
| iOS/Android ネイティブアプリ | △ アプリ開発コストが別途必要 |

## 5. 出版社との協業を踏まえたリアルな選択肢

**出版社が「強いDRMを要求」する可能性が高い**ので、現実的には：

### 案1：bookend に乗る（高コスト・最短）
- 出版社の信頼を取りやすい（業界実績あり）
- 初期240万 + 年間160万円 + ユーザー単価でコスト重い
- Avelia は「ベース写真集 + サインPDFを合成して bookend に納品」する受け側になる
- 開発工数は小さい

### 案2：Readium LCP で自社配信（中コスト・中工数）
- 年間費用のみで取引手数料なし → ユーザー数が増えても利益率が下がらない
- License Server + 閲覧アプリ開発が必要（Go + iOS/Android）
- 出版社にDRM要件を説明する必要あり

### 案3：自社開発で Web 閲覧型（最低コスト・割り切り）
- パターンYのオーバーレイ型 + 専用ビューワ
- DRM強度は妥協、**「ファンクラブの限定体験」として位置づけ** で出版社を説得
- スクショ漏洩は許容、流出時はログから追跡（透かし併用）

## 6. デモ・MVPとして検討すべき意思決定事項

実装に進む前に以下を確定する必要あり：

1. **出版社が要求する DRM レベル**
   - bookend等 商用DRM必須 / 透かしで足りる / Aveliaに委任
2. **配信形態**
   - ダウンロード可（パターンX, Z）/ Web閲覧のみ（パターンY）
3. **対応端末**
   - Webのみ / iOS/Android アプリも提供する
4. **予算感**
   - bookend の年間400万円超を許容できるか
5. **配信ボリューム**
   - 年何冊 × 何人想定（コスト試算の前提）

## 7. 推奨アプローチ

### フェーズ1（デモ）
- **パターンY + 自社開発 Web ビューワ**
- ベース写真集 PDF + サイン画像（PNG）を別管理
- ブラウザで `<canvas>` で重ね合わせて閲覧（既存のサイン入り動画デモと同じ思想）
- ダウンロード不可、スクショは目を瞑る
- **「ファンクラブの限定体験」としての立て付け**

### フェーズ2（本番・出版社協業時）
- 出版社のDRM要件次第で：
  - **強DRM必須 → bookend 連携**（Avelia は個別合成サービスとして bookend に納品）
  - **透かしで OK → Readium LCP または自社継続**

### フェーズ3（規模拡大時）
- iOS/Android ネイティブアプリで オフライン閲覧対応
- LCP ベースの自社エコシステム

## 8. 技術的に注意すべき点

### PDF合成（パターンX）の実装
- Node.js なら `pdf-lib`、Python なら `PyPDF2` / `reportlab`
- ベースPDFを読み込み → サイン画像を最終ページに重ねる → 新PDFとして書き出し
- 1ファイル100MB超の場合は処理時間・メモリに注意

### Webブラウザ閲覧（パターンY）の実装
- PDF.js でPDFをレンダリング、上に Canvas/SVG でサインを重ねる
- 右クリック禁止・DLボタン非表示・選択禁止 などの簡易対策
- スクショは諦める（OSレベルの機能を完全に防ぐのは不可能）

### スクショ漏洩の現実
- iOS/Android にはスクショ検知APIが存在（録画は別途）
- スクショ通知だけ出して**心理的抑止**にする運用は可能
- 完全防止は専用アプリ + ハードウェアレベルの対応が必要

## 9. コスト試算の参考

### ユーザー1万人・年間配信5冊の場合

| 案 | 初期 | 年間 | 取引時 |
|---|---|---|---|
| bookend | 240万円 | 160万円〜（ユーザー数で増加） | ファイル毎の処理費 |
| Readium LCP | 0（認証費のみ） | EDRLab認証料 + 自社サーバ | 0 |
| 自社開発（Web） | 0 | S3 + CDN 数万円 | 0 |

※ 開発工数は別途。Readium LCP・自社開発は閲覧アプリ開発で1000万円超え得る。
