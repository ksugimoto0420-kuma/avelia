# サイン入りデジタル写真集 技術調査レポート

出版社と協業してデジタル写真集にサインを付与し、ユーザーが手軽に閲覧できる
仕組みを実現するための事前調査。デモではなく **本番運用を前提に現実的な
実装方法と費用感を比較する**。

## 1. 業界における配信方式の3層構造

| Layer | 役割 | 主な選択肢 |
|---|---|---|
| コンテンツ形式 | 中身の入れ物 | PDF / EPUB（fixed-layout） |
| DRM | 不正コピー防止 | 強DRM（暗号化+鍵管理） / ソーシャルDRM（透かし） / なし |
| ビューワ | 閲覧手段 | Webブラウザ / 専用アプリ |

写真集はレイアウト保持が重要なので **PDF または EPUB fixed-layout** が主流。
DRM の強度をどうするかでサービス選びが変わる。

## 2. 競合サービス比較（2026年6月時点）

### 2-1. 強DRMグループ

#### bookend（KEYRING.NET）
- **コスト**：初期 240万円、年間ランニング 160万円〜
- **DRM**：暗号化、印刷制御、画面キャプチャ防止、閲覧期間制限、端末台数制限
- **個別納品**：ソーシャルDRM（透かし）でユーザー情報を動的埋込
- **対応**：iOS / Android / Web
- **実績**：sukisuki、ダブルの「PLANETS」など写真集配信で多数採用
- **特徴**：写真集向けで業界最高水準の保護、出版社の信頼を取りやすい

#### BookLooper（京セラコミュニケーションシステム）
- **コスト**：要見積（法人向け、初期 + 月額 + オプション）
- **DRM**：暗号化、コピー制限、閲覧期限、貸出期間管理
- **個別納品**：可（ユーザー認証ベース）
- **対応**：iOS / Android / Windows / Web
- **実績**：大学・企業 700+拠点、4.5万人ユーザー（三井住友海上等）
- **特徴**：法人・教育機関に強い、LDAP連携・学術認証連携あり

### 2-2. ライトDRMグループ

#### meclib（コトブキ企画）
- **コスト**：初期 3万円、月額 1万円〜（スタンダードコース、500ページまで）
- **DRM**：パスワード認証、簡易制御
- **個別納品**：△（個別ファイル単位の認証）
- **対応**：マルチデバイス（HTML5）
- **特徴**：**業界最安水準**、年間13万円台で運用可能、ただし強DRMはない

#### ActiBook（クラウドサーカス）
- **コスト**：フリープランあり、有料プランは要見積
- **DRM**：会員認証ベース、閲覧制限
- **個別納品**：◯（個別認証）
- **特徴**：閲覧ログ取得が強み、マーケティング寄り

#### FLIPPER U2（LOGOSWARE）
- **コスト**：月額/年額/従量制、要見積
- **DRM**：簡易DRM（保存・印刷制御）
- **特徴**：プリペイド・従量課金が選べる、小規模配信向け

#### ebook5（ルーラー）
- **コスト**：要見積
- **DRM**：軽量
- **特徴**：HTML5電子カタログをPDFから簡単生成、軽量配信向け

### 2-3. オープン規格

#### Readium LCP（EDRLab）
- **コスト**：EDRLab 認証料 年間数十万円、取引手数料ゼロ
- **DRM**：オープン標準の強DRM、ライセンス制御
- **個別納品**：ライセンスにユーザー情報を埋込可
- **対応**：自社で Readium ベースのアプリ開発が必要
- **開発コスト**：License Server（Go OSS）+ 閲覧アプリで 1000万円超え得る
- **特徴**：規模拡大時のランニング最適化向け

### 2-4. 自社開発

| 項目 | 内容 |
|---|---|
| コスト | サーバ実費のみ（S3/R2 + CDN で月数万円） |
| DRM | 限定的（透かし、簡易DRM、署名付きURL） |
| 個別納品 | ◯（完全制御） |
| 対応 | Web ブラウザのみ |
| 開発工数 | 中〜大（PDF.js 拡張 + 個別生成 + 配信API） |

## 4. 「サイン入り」を実現する3つの実装パターン

サイン入り写真集の本質は **「ベース写真集 + 個別サイン画像 = 個別納品物」**。

### パターンX：ファイル合成型（最も一般的）
1. アーティストが Avelia 管理画面でユーザーごとに「サイン+宛名」を描く
2. サーバー側で **ベース写真集PDFの最終ページにサインPDFを結合**
3. 生成された個別PDFを bookend / BookLooper / meclib 等に納品

- メリット：シンプル、出版社のコンテンツに手を加えない、強DRMサービスと相性◯
- デメリット：1ユーザーごとにファイル生成・保存が必要

### パターンY：オーバーレイ型（閲覧時合成）
1. ベース写真集（共通）と、サイン画像（個別）を別管理
2. 閲覧時にビューワが2つを **その場で重ねて表示**
3. ダウンロード不可、Webアプリのみで成立

- メリット：ファイル肥大化なし、サインの差し替え容易
- デメリット：ダウンロード提供不可、専用閲覧UI必須、自社開発寄り

### パターンZ：ソーシャルDRM型
1. ベース写真集の各ページに、購入者名/メール/購入IDを **透かし**として埋込
2. DRMは付けず、ダウンロード可
3. 流出時に出所が追跡できる

- メリット：自由度が高い、配布が楽
- デメリット：暗号化なし、「サイン」体験ではなく「透かし」、強DRM要求には不適

## 5. 現実的な実装案 3つ

ご相談の前提（スマホ中心、出版社交渉中、サインの見せ方は問わない、DL要否未定）
を踏まえると、選択肢は以下3つに絞られます。

### 第1案：Avelia は前処理に専念、配信は bookend に乗せる
**役割分担**：
- **Avelia**：管理画面でサインを描く → ベース写真集 + サイン を結合した個別PDFを生成
- **bookend**：生成済み個別PDFをユーザー単位で配信・閲覧

**Avelia 開発スコープ**：
- アーティスト向けサイン描画UI（既存のサイン納品機能の延長）
- ベース写真集の登録機能（管理画面でアップロード）
- 個別PDF生成バックエンドジョブ（Node.js pdf-lib 等）
- bookend API連携（ユーザー登録、ファイルアップロード、配信URL発行）

**コスト見積**：
- 初期：bookend 240万 + Avelia 開発 100〜200万
- 年間：bookend 160万〜（規模で増加）

**メリット**：強DRM要求をクリア、出版社の信頼◯
**デメリット**：ランニング高め、bookend 連携API実装が必要
**向くケース**：出版社が商用DRM必須を要求した場合

### 第2案：meclib + ソーシャルDRM（透かし）で割安に
**役割分担**：
- **Avelia**：個別PDF生成 + 購入者情報を透かしで埋込（流出追跡用）
- **meclib**：認証付きで配信、ブラウザ閲覧

**Avelia 開発スコープ**：
- サイン描画UI + 透かし埋込ロジック（PDFに薄く購入者情報を入れる）
- meclib API連携（あれば）or 手動アップロード運用

**コスト見積**：
- 初期：meclib 3万 + Avelia 開発 50〜100万
- 年間：meclib 13万〜

**メリット**：年間20万円程度で運用可能
**デメリット**：強DRMはない、流出時は透かし追跡のみ
**向くケース**：出版社が「透かしで追跡できればOK」と合意した場合

### 第3案：完全自社開発（Web閲覧、ダウンロード不可、パターンY）
**役割分担**：
- **Avelia**：すべて自社完結（保存・配信・閲覧UI）

**Avelia 開発スコープ**：
- ベース写真集の保存（S3/R2）
- サイン画像の保存
- 専用閲覧ページ（PDF.js + Canvas オーバーレイ）
- 署名付きURLでの配信、期限管理
- 透かし埋込（流出追跡用）

**コスト見積**：
- 初期：Avelia 開発 100〜200万
- 年間：S3/R2/CDN 月数万円

**メリット**：ランニング最小、サイン演出の自由度高い、Avelia エコシステム内完結
**デメリット**：「商用DRMがない」点で出版社の同意必須、スクショ漏洩許容
**向くケース**：「ファンクラブの限定体験」と位置づけて出版社と合意できた場合

## 6. 出版社交渉前に決めるべき3点

実装方針は **出版社との交渉次第** で大きく変わるので、先に下記を確認するのが
効率的：

### 6-1. コンテンツ保護の要求レベル
- 「Adobe DRM 相当を必須」→ **bookend / BookLooper 一択**
- 「透かしで追跡できればOK」→ **meclib / 自社開発 で成立**
- 「ファンクラブ限定の閉じた配信ならOK」→ **自社開発 で成立**

### 6-2. 配信形態の要求
- ダウンロード可能にすべきか / Web閲覧のみで良いか
- 専用アプリ必須か / ブラウザでOKか
- オフライン閲覧は必須か

### 6-3. 費用負担とビジネスモデル
- 配信プラットフォーム費用を**どちらが負担**するか
- 売上シェアの中に配信費を含めるか別請求か
- ユーザー数の見込み（ランニング費用に直結）

## 7. サイン部分の技術的注意点

### PDF合成（パターンX）
- Node.js: **pdf-lib** が標準的（既存PDFに画像を重ねる、ページ追加など）
- Python: PyPDF2 / reportlab
- 1ファイル100MB超の場合は処理時間・メモリに注意（バックエンドジョブ化）

### 個別PDF生成のフロー例
```
[出版社]
  ベース写真集 PDF をアップロード
       ↓
[Avelia 管理画面]
  購入者リストから「次のユーザー」を選択
  サイン描画ボード（既存のサイン納品機能と同じ仕組み）
  → サイン PNG を生成
       ↓
[Avelia バックエンドジョブ]
  ベース PDF + サイン PNG を pdf-lib で結合
  購入者IDを透かしとして全ページに埋込（パターンZ寄せ）
  → 個別PDF を生成
       ↓
[配信プラットフォーム]
  生成済み PDF をアップロード or 自社で配信URLを発行
       ↓
[購入者]
  メール通知 → 視聴ページへ
```

### Webブラウザ閲覧（パターンY、自社開発時）
- **PDF.js** でPDFをレンダリング、上に Canvas/SVG でサインを重ねる
- 右クリック禁止・DLボタン非表示・選択禁止 などの簡易対策
- スクショは諦める（OSレベルの機能を完全に防ぐのは不可能）
- 透かしを薄く重ねて流出時の追跡を可能にする

### スクショ漏洩の現実
- iOS/Android にはスクショ検知APIあり（録画は別途）
- スクショ通知だけ出して**心理的抑止**にする運用は可能
- 完全防止は専用アプリ + ハードウェアレベルの対応が必要

## 8. 推奨アクション（優先順）

1. **出版社にヒアリング** — DRM要求レベル、配信形態、費用負担を確認
2. **bookend / BookLooper / meclib の3社に問い合わせ** — 実見積、サイン入り対応の可否、API連携可否
3. **結果を踏まえて第1〜3案を選択**
4. その上で Avelia 側の開発スコープを確定
5. プロトタイプ作成（必要なら）

## 9. 自社開発が向く / 向かないの判断軸

### 自社開発が向くケース
- ファンクラブ限定の閉じた配信（出版社の同意済み）
- 配信規模が小〜中（数百〜数千人）
- ランニング費用を抑えたい
- サイン演出の見せ方にこだわりたい
- 「ガチDRMは要らない、流出時は法的対応で」の方針

### 自社開発が向かないケース
- 出版社が商用DRMを要求
- 配信規模が大（数万人〜）でアプリ含む対応が必要
- スクショ漏洩リスクを完全に許容できない
- iOS/Android のオフライン閲覧が要件
- 業界標準のDRM実績で出版社を説得したい
